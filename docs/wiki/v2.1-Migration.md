# v2.1 Migration guide

`@nestjs-crud/prisma@2.1.0` narrows the `@prisma/client` peer range from `>=5.0.0` to `^7.0.0`. Prisma 5 and 6 are no longer supported. The adapter's runtime API is unchanged: your `extends PrismaCrudService<T>` subclass compiles and runs against Prisma 7 with zero code changes. The migration work lives entirely in your Prisma schema and CLI invocations, not in the adapter.

The other six packages (`@nestjs-crud/util`, `request`, `core`, `typeorm`, `drizzle`, `mikro-orm`) publish at `2.1.0` with no behavior change. The coordinated version bump exists so `^2.0.0` ranges pick up the Prisma peer change automatically.

## TL;DR

- **Peer range:** `@prisma/client >=5.0.0` → `^7.0.0`.
- **Adapter runtime API:** unchanged. No subclass rewrites.
- **Required if you maintain a `schema.prisma`:** remove `datasource.url`; add a `prisma.config.ts` forwarding `DATABASE_URL`.
- **Required if you invoke `prisma db push` in scripts:** drop the `--skip-generate` flag (removed in v7).
- **Required at runtime:** adopt a driver adapter (`@prisma/adapter-pg`, `@prisma/adapter-mariadb`, `@prisma/adapter-neon`, `@prisma/adapter-planetscale`, etc.). v7 `PrismaClient` no longer reads `env.DATABASE_URL` implicitly and rejects `datasourceUrl` and `datasources.db.url` against v7-shaped schemas.
- **Non-trivial Postgres or MySQL setups:** read the [Driver adapter gotchas](#driver-adapter-gotchas) section. Two landmines are not in the upstream docs.
- **Other six `@nestjs-crud/*` packages:** version-only republish at `2.1.0`. No code changes.

> **Want to stay on v2.0.x?** Pin `"@nestjs-crud/prisma": "^2.0.0"` and `"@prisma/client": "^5 || ^6"`. `npm update` will continue tracking the v2.0.x line. There is no `v2.0-lts` dist-tag; `latest` flips to `2.1.0`.

## Am I affected?

**Yes**, if you are on `@nestjs-crud/prisma@2.0.x` with `@prisma/client@5.x` or `@6.x` and want to upgrade to `2.1.0`.

**No**, if you already run `@prisma/client@7.x` with a v7-shaped schema and driver adapters.

**Partially:** if you consume only the non-Prisma `@nestjs-crud/*` packages (`typeorm`, `drizzle`, `mikro-orm`, `core`, `request`, `util`), the `2.1.0` bump is a version-only republish. Bump freely; no code changes required.

## Prerequisites

- **Node.js `>=22.0.0`** (unchanged from 2.0).
- **`@prisma/client ^7.0.0`** and **`prisma ^7.0.0`** (dev-dep).
- **A driver adapter package** matching your database: `@prisma/adapter-pg` (Postgres), `@prisma/adapter-mariadb` (MySQL / MariaDB), `@prisma/adapter-neon` (Neon), `@prisma/adapter-planetscale` (PlanetScale), `@prisma/adapter-d1` / `@prisma/adapter-libsql` (Cloudflare D1 / Turso).

## Upgrade command

```bash
yarn up @nestjs-crud/util@2.1.0 @nestjs-crud/request@2.1.0 @nestjs-crud/core@2.1.0 \
        @nestjs-crud/typeorm@2.1.0 @nestjs-crud/drizzle@2.1.0 @nestjs-crud/mikro-orm@2.1.0 \
        @nestjs-crud/prisma@2.1.0
yarn add @prisma/client@^7
yarn add -D prisma@^7
yarn add @prisma/adapter-pg        # or adapter-mariadb / adapter-neon / adapter-planetscale
```

## High-blast breaking changes

These changes affect every consumer running Prisma. Each has a before/after block.

### 1. Remove `datasource.url` from `schema.prisma`

Prisma 7 rejects `url` inside the `datasource` block. `prisma generate` on a v5-shaped schema errors with `The property url on the datasource block is not allowed.`

```prisma
// v5 / v6 — before
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

// v7 — after
datasource db {
  provider = "postgresql"
}
```

Migration: remove the `url = env("DATABASE_URL")` line from every `schema.prisma` in your project. The URL now lives in `prisma.config.ts` (for the CLI) and in the driver adapter's connection config (for the runtime client). See the next two sections.

### 2. Add `prisma.config.ts` and forward `DATABASE_URL` explicitly

Prisma 7's Migrate CLI (`prisma db push`, `prisma migrate`) requires the datasource URL to be declared in `prisma.config.ts`. Env-populated `DATABASE_URL` is no longer auto-discovered by the CLI; your config file must forward it.

Create `prisma.config.ts` at your project root (or pass `--config <path>` to CLI invocations):

```ts
import { defineConfig } from 'prisma/config';

export default defineConfig({
  schema: 'prisma/schema.prisma',
  datasource: {
    url: process.env.DATABASE_URL!,
  },
});
```

Multi-dialect projects can compute `schema` at the top of the file (off a `PRISMA_DIALECT` env var, for example) and pass it into `defineConfig` the same way.

The `datasource.url` forward is required. A config file with `schema` only will error on `db push` with `The datasource.url property is required in your Prisma config file`. This is the most subtle of the v7 breakages: the error message points at the schema block, but the fix is in the config file.

### 3. Drop `--skip-generate` from `prisma db push`

The `--skip-generate` flag was hard-removed in v7. `prisma db push --skip-generate` errors with `Unknown argument '--skip-generate'`. `db push` now always runs `generate`. Prisma 7's own upgrade notes list the flag as "deprecated" without a compatibility fallback, so CI scripts, Dockerfiles, and `package.json` scripts will hit it cold.

Migration: grep your repo and drop every occurrence of the flag from `prisma db push` invocations:

```bash
grep -rn "skip-generate" . --include='*.json' --include='*.yml' --include='*.yaml' \
                           --include='Dockerfile*' --include='*.sh'
```

### 4. Replace `PrismaClient` env-URL construction with a driver adapter

Prisma 7's `PrismaClient` constructor rejects `datasourceUrl` and `datasources.db.url` when the schema omits `url` (which it now must, per §1). The client also stops reading `env.DATABASE_URL` implicitly. The only supported non-Accelerate runtime path is a driver adapter.

All three v5 / v6 patterns throw on v7 — `new PrismaClient()` (implicit env), `new PrismaClient({ datasourceUrl })`, and `new PrismaClient({ datasources: { db: { url } } })` — with `Your Prisma Client was configured with datasourceUrl, but the datasource in schema.prisma does not expose a URL.`

```ts
// v7 — Postgres
import { PrismaClient } from '@prisma/client';
import { PrismaPg } from '@prisma/adapter-pg';

const prisma = new PrismaClient({
  adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL! }),
});

// v7 — MySQL (replace the adapter import + ctor):
import { PrismaMariaDb } from '@prisma/adapter-mariadb';
const prisma = new PrismaClient({ adapter: new PrismaMariaDb(process.env.DATABASE_URL!) });
```

Wire it into your NestJS module provider exactly as before. `PrismaCrudService<T>` receives the client through its existing constructor. No subclass changes.

See [ServicePrisma — Connection options](https://github.com/kodjunkie/nestjs-crud/wiki/ServicePrisma#connection-options) for the full per-adapter matrix (Postgres / MySQL / PlanetScale / Neon / Cloudflare D1).

## Driver adapter gotchas

Two driver-adapter behaviors are not covered in Prisma 7's release notes or in the adapter READMEs. Consumers with non-trivial Postgres or MySQL setups hit them blind. This wiki page is the authoritative warning.

### Gotcha 1 — `@prisma/adapter-pg` does not run `SET search_path`

**Symptom.** Against a Postgres database where your tables live in a non-`public` schema (multi-tenant setups, or roles with a custom default `search_path`): `prisma db push` creates tables in `public` anyway, even with `?schema=custom` in `DATABASE_URL`; runtime queries fail with `relation "Foo" does not exist`; raw-SQL calls like `$executeRawUnsafe('ALTER SEQUENCE "Foo_id_seq" ...')` fail on sequences that exist in your schema.

**Cause.** `@prisma/adapter-pg` forwards the connection string to `node-postgres`'s `Pool` but does not emit `SET search_path TO <schema>` after the connection opens. The Prisma engine process (v5 / v6) did this for you implicitly.

**Workaround.** Pass libpq's `options=-c search_path=<schema>` in the pg `PoolConfig` so every pooled connection runs the `SET` at startup, and pass the same schema as the second `PrismaPg` argument (sets `ConnectionInfo.schemaName` so the ORM query builder qualifies table names in generated SQL). You need both: `schema` alone covers ORM SQL; `options` alone covers raw SQL.

```ts
import { PrismaClient } from '@prisma/client';
import { PrismaPg } from '@prisma/adapter-pg';

const u = new URL(process.env.DATABASE_URL!);
const schema = u.searchParams.get('schema') ?? undefined;
u.searchParams.delete('schema');

const pgConfig: Record<string, unknown> = { connectionString: u.toString() };
if (schema) pgConfig.options = `-c search_path=${schema}`;

const adapter = new PrismaPg(pgConfig, schema ? { schema } : undefined);
const prisma = new PrismaClient({ adapter });
```

### Gotcha 2 — `@prisma/adapter-mariadb` does not persist session state across calls

**Symptom.** Silent behavior drift when code relied on `SET SESSION` state (`sql_mode`, `time_zone`, `FOREIGN_KEY_CHECKS`, user variables `SET @x`) persisting across statements. Two common cases: (1) teardown scripts using `SET FOREIGN_KEY_CHECKS = 0; TRUNCATE t1; ... SET FOREIGN_KEY_CHECKS = 1;`. The toggle does not persist; TRUNCATE fails on FK constraints. (2) User variables (`SET @x = 1; SELECT @x;`) return `NULL` on the second statement.

**Cause.** `@prisma/adapter-mariadb` dispatches each `$executeRawUnsafe` and `$queryRawUnsafe` on a fresh checkout from the mariadb pool. Session-scoped `SET` state does not persist across checkouts. The Prisma engine process (v5 / v6) held one connection for the life of the client, so session state survived.

**Workaround for FK-constrained teardown.** Refactor to dependency-ordered `DELETE FROM` plus `ALTER TABLE ... AUTO_INCREMENT = 1`. No FK toggles needed:

```ts
// v7
await prisma.user.deleteMany({});       // children first
await prisma.company.deleteMany({});    // then parents
await prisma.$executeRawUnsafe('ALTER TABLE `User` AUTO_INCREMENT = 1');
await prisma.$executeRawUnsafe('ALTER TABLE `Company` AUTO_INCREMENT = 1');
```

**Workaround for required session state (`sql_mode`, `time_zone`, custom variables).** Configure the mariadb pool's `initSql` (or equivalent connection-open hook) to replay the `SET SESSION` statements on every new connection. Consult the `@prisma/adapter-mariadb` source for the current pool-config surface.

## Low-blast changes

- `@nestjs-crud/prisma` runtime API is unchanged. No deleted or renamed methods. No constructor shape change. No signature tightening.
- `@nestjs-crud/util`, `request`, `core`, `typeorm`, `drizzle`, `mikro-orm` publish at `2.1.0` with no behavior change. The bump exists so `^2.0.0` resolution pulls the Prisma peer change for any consumer installing multiple adapters.
- No CLI or config changes on the adapter side.

## New features

None in this release; it is a peer-range bump.

The driver-adapter pattern is the new default connection path in Prisma 7's story. See [ServicePrisma — Connection options](https://github.com/kodjunkie/nestjs-crud/wiki/ServicePrisma#connection-options) for examples across Postgres, MySQL, PlanetScale, Neon, and Cloudflare D1.

## Removed v2.0 surfaces

None. The adapter's constructor, public method signatures (`getMany`, `getOne`, `createOne`, `createMany`, `updateOne`, `replaceOne`, `deleteOne`, `recoverOne`), and internal composition (`QueryTranslator` + `WhereBuilder` + `QueryComposer` + `FetchHelper`) are unchanged.
